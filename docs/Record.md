# 录音链路说明

## 目标

录音链路分两条：

1. 手机录音：先录成 WAV，停止后直接交给音频模型。
2. 戒指测试链路：先收音频 Buffer，再批量组装成 WAV，最后交给音频模型。

## 手机录音

- 点击开始时只申请麦克风权限并启动录音。
- 录音阶段不做实时识别，避免 `AVAudioEngine installTap` 这类高频回调导致崩溃。
- 停止录音后读取 WAV 文件，直接发送到阶跃音频模型。

## 戒指测试链路

1. RX 收到原始音频 Buffer。
2. App 只做轻量处理：校验顺序、写入队列。
3. 每 2 秒从队列中取出一段连续音频。
4. 将 Buffer 按顺序拼成 PCM 流，再封装成 WAV。
5. 把 WAV 作为 `input_audio` 送入阶跃音频模型。
6. 模型直接返回润色文本、摘要和意图卡片。

## Buffer 如何变成文字

Buffer 本身不是文字，而是原始音频数据。现在不再单独转写，转换过程可以理解为：

```text
BLE Buffer -> PCM 缓存 -> WAV -> 音频 AI -> 索引卡 -> 页面展示
```

关键点有两个：

- 先保证音频包顺序正确，只记录批次摘要，不把每个包都刷到日志区。
- 再把完整音频片段送入音频模型，不要逐包调用 AI。

## UI 策略

- UI 只展示当前最新识别结果。
- 日志区只显示批量摘要和状态变化。
- 不要在每个 Buffer 到达时刷新整页。

## 阶跃音频接口

- `step-audio-2` 的音频请求需要 `modalities: ["text", "audio"]`。
- 请求体需要顶层 `audio.format: "wav"`，否则会返回参数错误。
- 有效文本结果优先从 `message.audio.transcript` 读取，`message.content` 可能为空。
- 模型可能返回非目标 JSON，App 需要直接报错并展示原始片段，不能假装成功。
- HTTP 500 `engine_exception` 表示服务端处理音频失败，优先核对 WAV 是否为空、采样率是否为 16 kHz、是否为单声道 16 bit PCM。

## 结论

戒指侧是流式 Buffer 传输，App 端应采用“缓冲队列 + WAV 组装 + 音频 AI”的方式处理。文档里要明确区分三件事：原始音频 Buffer、模型返回的结构化结果、页面最终展示的索引卡。
